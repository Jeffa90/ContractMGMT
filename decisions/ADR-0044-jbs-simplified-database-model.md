# ADR-0044: Simplified database model for the JBS IIS deployment (Row-Level Security and the ecp_runtime role retired)

Status: Implemented on branch jbs/iis-integration. Owner decision 2026-11-18, approving `docs/JBS_DATABASE_SIMPLIFICATION_REVIEW.md`. Supersedes ADR-0003 decision detail 2 for the SQL Row-Level Security layer only; every other part of ADR-0003 stands. Production approval remains external governance and is not declared.

## Context

ADR-0003 chose layered tenant isolation for three product modes, including multi-tenant hosting: TenantId on owned entities, EF global query filters, SQL Server Row-Level Security (RLS) through `SESSION_CONTEXT`, composite foreign keys that include TenantId, and tenant-prefixed storage keys. RLS also needed an application-created database role (`ecp_runtime`).

The JBS deployment is one application, one database and one tenant. Setup creates exactly one tenant, and tenancy can be widened after setup only to several organisations inside that tenant. RLS enforces the tenant boundary only; it never enforced organisation, business unit, division, site, category, ownership or classification access, which the application enforces. Keeping RLS cost the migration account `CREATE ROLE` and `ALTER ANY SECURITY POLICY`, required the DBA to add the runtime account to an application role, filtered rows from the DBA's own queries, and added a session-context round trip. The review found that the runtime account works with db_datareader + db_datawriter and that the audit trail is protected by its append-only trigger for every login.

## Decision

1. **Removed:** the `ecp_runtime` database role; all tenant security policies; the RLS predicate functions and the `security` schema; the `SESSION_CONTEXT` plumbing used only for RLS (`ScopedConnection` and the command interceptor no longer set it); the RLS-specific readiness, restore and upgrade checks (R-DB-02 no longer looks for the role; VAL-008 session-context isolation is removed; VAL-007 now checks that no retired RLS object remains; the post-upgrade policy comparison is removed).
2. **Kept, unchanged:** `sp_getapplock` for audit-chain concurrency; EF Core's own migration lock; the audit append-only trigger; TenantId on every owned entity; composite foreign keys that include TenantId; EF global tenant query filters (fail closed); refusal of writes to another tenant; all application-layer organisation, business-unit, site, category, ownership and classification security; SQL-backed operation leases.
3. **Explicit tenant predicates.** Every reviewed raw SQL statement that reads tenant-owned rows (backup and restore inventories, post-restore validation, the support bundle) now states `TenantId = @tenant` itself; before, RLS supplied that filter.
4. **Migrations.** The historical helpers `CreateInfrastructure`, `AddTenantPolicy`, `DropTenantPolicy`, `GrantRuntimeAccess` and `DropInfrastructure` emit nothing, and the one direct `DENY ... TO [ecp_runtime]` line in Audit migration `20261016000541_Initial` was removed; no other historical migration was edited. One forward migration, Audit migration `20261118000000_RemoveRowLevelSecurity`, removes every retired object where it exists, each statement guarded by an existence check, so on a fresh installation it does nothing.
5. **Release integrity.** The 31 historical migrations whose generated SQL changed are recorded as owner-approved amendments in `upgrades/migration-reviews.json` (module, migration, old checksum, new checksum, `ADR-0044`, reason). The upgrade checks UPM-012 and UPF-015 and the post-upgrade record check UPV-001 accept a changed checksum only when it is exactly a recorded amendment; any other difference still fails as tampering. The 1.0.0-to-1.1.0 manifest was rebuilt from the release notes with `upgrade-manifest-build` and verifies with `upgrade-manifest-verify`.
6. **SQL permissions.** Migration account: db_ddladmin + db_datareader + db_datawriter. Runtime account: db_datareader + db_datawriter. Not required: db_owner, db_securityadmin, `CREATE ROLE`, `ALTER ANY SECURITY POLICY`, `ecp_runtime` membership. R-DB-02 flags a runtime login that is sysadmin, db_owner or able to change the schema.
7. **Scope.** This is a JBS deployment decision. Multi-customer / multi-tenant hosting is **unsupported** for this deployment unless database-level tenant isolation is reintroduced (a future ADR).

## Databases created before this decision

No JBS database exists yet, so JBS starts with the simplified model. A database created by an earlier version still holds the policies; this version sets no session context, so those policies would hide every row from the application, and the pre-flight's inventories would read nothing. Such a database is cleaned before the upgrade pre-flight: after a verified backup a DBA runs `deploy/sql/remove-retired-row-level-security.sql` (the same SQL as the forward migration, kept identical by a test; it needs ALTER ANY SECURITY POLICY and control of the role, so db_owner or equivalent, for that one run). VAL-007 / UPF-053 fails with that instruction while any retired object remains. On a non-Production database `dotnet Ecp.Host.dll migrate` applies the forward migration, which does the same.

## Consequences

* The DBA grants only standard database roles; no application-created role, no security policy, no rows hidden from the DBA's queries.
* Tenant isolation rests on the application layers, the composite foreign keys and the architecture tests that ban `IgnoreQueryFilters` and unwrapped raw SQL in application code. A missed filter in application code would no longer be caught by the database; with one tenant there is no other tenant's data for it to expose.
* Master instruction D1 ("TenantId on owned entities, query filters, service policies, database constraints and cross-tenant tests") is still met: the composite foreign keys are the database constraint, and the cross-tenant tests run at the application layer on SQL Server. CONFIRMED_DECISIONS D4's "Row-Level Security" test clause is not applicable to this deployment; SQL Server tests instead prove that no RLS object exists and that a database holding them is cleaned without losing a row.
* Reversal: reintroducing RLS is a new forward migration plus restoring session context; the retired helpers' history and this ADR describe exactly what existed.

## Verification

`SqlServerSimplifiedModelTests` (fresh install with exactly db_ddladmin + db_datareader + db_datawriter; no retired object afterwards; runtime with db_datareader + db_datawriter works and cannot change the schema, disable, alter or drop the audit trigger, or update or delete audit events; a database holding the retired objects is cleaned by the forward migration with every row kept and the DBA script is safe to run again), `SqlPermissionProbeTests` (DBA report), `RuntimePrivilegeSqlServerTests` (R-DB-02), `SqlServerBehaviourTests` (no policy, application filter isolation, fail closed without a scope, cross-tenant write refused, composite foreign keys, gap-free concurrent audit writes under `sp_getapplock`), `AccessScenarioTests_SqlServer` and the classification scenarios (organisation, business unit, site, category and classification controls), backup/restore and post-restore validation, the N-1 to N upgrade rehearsal, `DatabaseSimplificationGuardTests` (no session context, security policy or role in compiled code; the helpers emit nothing; the DBA script equals the migration SQL; `sp_getapplock` and the trigger kept), and the release-integrity test (every baseline difference is a recorded amendment). All run in CI on SQL Server 2022 and 2025.
