# ADR-0036: Operations dashboard, operational probes and the observability foundation

Status: Implemented by slice OPS-03 (2026-10-18). Proposed until the owner reviews it; production approval remains external governance.
Builds on ADR-0003 (tenant isolation and row-level security), ADR-0034 (operational resilience), ADR-0035 (upgrade safety). Owner decisions: `requirements/01-authoritative/CONFIRMED_DECISIONS.md`, section D12. Scope and contradictions: `docs/OPS03_REQUIREMENTS_MATRIX.md`.

## Context

OPS-01 and OPS-02 gave an operator backup, restore, validation, maintenance mode, leases, upgrade pre-flight, rehearsal and rollback evidence, each on its own page. What the operator could not do was **see the whole installation at once**: whether jobs are running, whether the outbox is draining, whether packs and keys are still acceptable, whether the last backup is recent, and what failed most recently. `requirements/12-operations/SETUP_AND_READINESS_SPEC.md` section 6 describes that dashboard; `TASKS.md` OPS-03 names its panels (health, readiness, jobs, outbox, certificates).

## Decision

1. **One service builds the dashboard; pages only show it.** `IOperationsDashboard` (in `Ecp.Recovery`, beside the services it reuses) assembles ten panels: installation health, readiness catalogue, platform and schema versions, upgrade readiness and migrations, backup and restore, background jobs and leases, notification outbox, packs and configuration, document store and audit chain, certificates and secret expiry. It reuses `ReadinessService`, `IOperationHistory`, `IOperationLeases`, `IMaintenanceService`, `IBackupCatalogue`, the last validation, the migration inventory and the upgrade state detector. The Razor page model has one line per handler; an architecture test forbids page models in the Operations admin folder from touching a database, a connection, a readiness check or a lease directly.
2. **Four distinct states, one rule.** Every line is **Verified**, **Warning**, **Failed** or **Not Verified**. A panel is its worst line and the dashboard is its worst panel, in the order Failed, Not Verified, Warning, Verified (the same order as the upgrade pre-flight). Not Verified means "nobody has looked, or it cannot be looked at here"; it is never merged into a pass, and an empty set is Not Verified. The page prints the word, not only a colour.
3. **Tenant data is reached only through probes that return counts and times.** `IOperationalProbe` (in `Ecp.SharedKernel`, beside `IUpgradeProbe`) returns `OperationalFact(Area, Key, long Value, DateTime? Utc, Combine)`. The type cannot carry text. Notifications (outbox and jobs), Data Migration (batches) and Configuration (releases in force, packs, signing-key expiry) each contribute one. `OperationalFactCollector` calls each probe once per tenant inside that tenant's own scope (row-level security applies exactly as in normal use) and combines the facts. The installation dashboard therefore never reads another tenant's record, never shows a recipient, subject, name or error text, and offers no cross-tenant action: retrying a dead-lettered message stays with that tenant's administrator.
4. **The readiness catalogue is shown whole.** The 30 checks of the specification are listed. Those that run (the platform checks, plus three derived from the dashboard's own facts) show their result; those that exist only in the setup wizard or as the start-up guard are shown as Not Verified with that reason; those not built are Not Verified, "not built". SET-03 (the full catalogue) is not claimed.
5. **Certificates and secrets, only what is readable.** Pack-signing keys (validity dates), the data-protection key ring (through a neutral `IKeyRingInspector` the host implements; expiry only, never keys), and the backup-encryption certificate (Not Verified: it lives on the database server). **TLS certificate** and **secret expiry** are Not Verified, with the reason.
6. **Failures are shown, never softened, and retry is offered only where valid.** The failure register lists recent failed or incomplete operations with the last result, time, correlation id and the next step. A failed backup, validation, rehearsal or rollback-evidence run offers "start a new attempt" (a fresh run, never a resume). A failed **restore or upgrade is never retried**, maintenance mode stays on, and the entry says what to do. A run recorded as running with no live lease, a lease that expired without release, and a job run stuck as running are flagged. The dashboard changes nothing.
7. **Least privilege.** `operations.read` in the installation tenant reads the dashboard; `operations.validate` additionally reveals technical detail. No new permission (the specification's `ops.manage` is read as the D10 set). The support bundle needs `operations.evidence.export` and a recent sign-in.
8. **Observability foundation.** The standard .NET `Meter` named `Ecp.Operations`: counters for finished operations (kind, status), background-job cycles (outcome) and dashboard builds; observable gauges for outbox, jobs, leases and panel statuses (read from the last dashboard build). Structured `LoggerMessage` events carry the correlation id; failures log as warnings so they reach the support bundle's redacted lines. Tags are fixed words; no tenant, person, record or error text is ever a tag. `OperationHistory.FinishAsync` and the background-job cycle are instrumented additively (no behaviour change). **No exporter is configured or verified**: OpenTelemetry, syslog and SIEM sinks belong to INT-04 and are Not Verified / Future; the Meter is what such a sink would subscribe to.
9. **Support bundle completion (the part the dashboard needs).** Generation needs a recent sign-in as well as the permission and is one audited act (size, SHA-256, correlation id; nothing is kept on the server, so there is nothing to expire). The bundle gains a deterministic `manifest.json` (every entry's name, size and SHA-256, fixed order), a formula-safe summary spreadsheet, the operational facts, the metrics snapshot and the generation correlation id; entry names are an allow-list, with a size cap per entry and in total; archive timestamps are fixed. SEC-030 and SEC-031 (OPS-04) are not claimed.
10. **Anonymous health stays minimal.** In Production `/health/ready` returns the overall status only; Demo and Test (never internet-facing) keep the per-check list because the container smoke test relies on it. The shaping is `HealthBodies.Ready`, unit tested. Detailed dependency information is on the authorised dashboard only.

## Consequences

* A trained operator opens one page and sees what is healthy, what needs attention, what failed last and why, what was never checked, and where to go next, without a development tool.
* Adding a module's operational signal is one small probe class; the dashboard needs no change to its structure.
* The dashboard is a read; it adds no migration and no table. Probe facts are computed on request (counts); on a large installation the build cost grows with the number of tenants and is bounded by the probes' simple counts.
* Not Verified will be visible on the page until SET-03 builds the remaining checks, INT-04 adds sinks and the deployment models are exercised. That is deliberate.
