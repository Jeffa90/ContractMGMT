# ADR-0041: Guided field administration over the unchanged custom-field engine

Status: Implemented on the guided-administration branch (UX-10). Proposed until the owner reviews it; production approval remains external governance and is not declared.
Builds on ADR-0039 and ADR-0040 (a presentation layer over the existing services) and on the custom-field engine of CFG-03, which this decision leaves as it was.

## Context

Manual testing found that adding a custom field was hard enough that an administrator could not tell whether the feature worked. The engine was never the problem (definitions are a draft, validated, published, versioned, rolled back and audited, and values sit in typed columns). The pages in front of it asked for things a business administrator should never see: a field key to invent and type, choices written as `CODE | Label | inactive`, a "Start a draft" step before anything could be changed, every setting of every type on one page whatever the type, and a separate validate step and publish page. Nothing showed the field as it would appear on the form, and the page that put it in force did not say what it would do for this person (publish, or submit for a second person).

## Decision

1. **Replace the front door, not the engine.** A new set of pages under `/Admin/Fields` (menu: Administration, Contracts & Metadata, Fields) is the standard way to manage fields. It calls the same `ICustomFieldStudio`, so the draft, validation, publication, second-person rule, history, rollback and audit are exactly those of every configuration document. No change was made to the metadata module, the field document, the value table, or the validator. The older Studio pages remain, labelled advanced, because sections, shared lists and shared views are still edited there and existing links keep working.
2. **A landing page, then a guided editor.** The Fields page lists Field, Type, Section, Used on, Required and Status, with **+ Add field**, a search box, and per row **Edit**, **Preview**, **Retire** (or **Reinstate**) and **Version history**. Status is derived by comparing the open draft with what is in force ("Published", "New, not published yet", "Changed, not published yet", "Retiring, not published yet", "Retired").
3. **The editor asks in the order a person thinks.** Basic information; field type (a plain-language picker of the engine's 17 types); only the settings that belong to the chosen type; a choice editor for choice fields (add, reorder, switch off, remove an unused option; no code and no JSON); placement (section, new section, display order); Rules (standard: required, searchable, filterable, sortable, reportable, offered only where the type allows them; **Advanced**, collapsed: who sees it, who can change it, stages, types, classification, dates, use in approval rules, and the technical name); a preview drawn by the **same partials** the real Create and Details pages use; and a review in plain English. Mistakes are explained in words ("Give the field a name.", "The option \"30 days\" appears more than once.").
4. **Machine names are generated and hidden.** The field key is made from the name (lower-case, never a core field's key, never one already used, retired fields included). A choice's stored code is made from its label ("30 days"), so the stored value reads naturally and never changes when the label is edited. Both appear only under Advanced, read-only after publication.
5. **No draft step.** The first change opens the organisation's draft. A single panel ("Changes waiting to be published") lists what will go in force together, shows the checks in words, and offers **Publish**, **Submit for publication**, or **Review and publish** according to the same governance information the other configuration pages use (`GovernanceAsync`). Publishing needs the recent sign-in the other configuration pages need, which is why the save and the publish are separate requests.
6. **Placement is honest about what the engine does.** The engine has no switches for Create, Edit and Details separately: every field that is current and not calculated is on New and Edit, every visible field is on Details, and who sees or changes it is governed by roles, stages and classification. The pages say exactly that and show "Used on" from the real rules. They do **not** add three checkboxes that would do nothing. Independent per-surface switches would be a change to the field document and are recorded as a decision for the owner (below).
7. **Exports include the new fields on request.** A shared or system view lists fixed columns, so a newly published field was not in an export unless a shared view was edited in the Studio. The register's export form gains **Include the additional fields** which adds every reportable field the person may see to that export's columns, using the export request's existing `Columns` parameter. The reportable flag, the person's classification and role rules, and the export permission still decide what is in the file.
8. **One backend defect found and fixed** (not in the metadata engine; in the contracts module's use of it): the Create path did not apply the classification gate that Details, Edit, Save and the register apply. A creator whose ceiling is below a field's classification was offered the field and could write a value they could never read back. Now the field is neither offered nor accepted on Create for such a creator (a creator who holds no read right at all is not narrowed, as before). This is reported separately from the usability failures.

## Alternatives considered

* **Edit the older Studio field page in place.** Rejected: its structure (one page, all types, a key field, text-syntax choices) is the problem, and existing tests and links depend on it.
* **Add Create/Edit/Details flags to the field document.** Rejected for now: it changes the engine, the validator, the parser and every consumer, and nothing in the acceptance scenario needs it. Recorded for the owner.
* **Auto-add every new field as a column of every view.** Rejected: views are separate configuration with their own draft and publication; surprising people's views is worse than one export checkbox.
* **Publish from the editor in the same request as the save.** Rejected: publication needs a recent sign-in; a redirect to confirm identity would lose the form. Two requests keep the work safe.

## Consequences

* No migration, no schema change, no change to the upgrade manifest.
* Existing fields, drafts and releases are read exactly as before; a field created on the old pages is edited on the new ones and the reverse.
* Open for the owner: independent Create/Edit/Details switches (engine change); adding a new field as a column of a shared view from the Fields pages; guided editing of choice lists shared between fields (still the older Lists page).
