# ADR-0035: Upgrade safety: pre-flight validation, forward-only migrations, N-1 to N rehearsal and rollback by restore

Status: Implemented by slice OPS-02 (2026-10-18). Proposed until the owner reviews it; production approval remains external governance.
Builds on ADR-0003 (tenant isolation and row-level security), ADR-0011 (audit chain), ADR-0026 (external packs), ADR-0034 (backup, restore, maintenance mode and leases). Owner decisions: `requirements/01-authoritative/CONFIRMED_DECISIONS.md`, section D11.

## Context

OPS-01 gave an operator a verified backup and a restore that is proved on a populated installation. What was still missing is the answer to the question asked before every release: **can this installation be upgraded safely, and what do we do if it goes wrong?** Until now an operator could run `migrate`, which applies whatever migrations the running build carries, to whatever database it is pointed at, with no check of what the database holds, no requirement for a backup, and no evidence afterwards.

## Decision

1. **Installation-level, forward-only.** An upgrade moves a whole installation from one released platform version to the next. Migrations only go forward. There is no downgrade operation anywhere in the product: no command, no page, no service method (a test asserts this).
2. **Rollback is restore.** The only supported way back is to restore the verified pre-upgrade backup, with the application version that made it. The platform proves this path with a separate rollback-evidence run that restores the backup into a new database and validates it, and it states plainly that work done since the backup is discarded (the data-loss window).
3. **The release carries its own description: the upgrade manifest.** Each build embeds (`upgrades/`, as resources of `Ecp.Recovery`):
   * a **frozen baseline ledger** per released version: every module, every migration identifier and its checksum, hashed. Baselines are committed once and never regenerated;
   * the **release notes** the release engineer writes (supported sources, packs, configuration changes, requirements, operational actions, compatibility warnings, breaking changes, post-upgrade checks);
   * the **upgrade manifest** built from baseline + notes + the migrations compiled into this build: deterministic, canonical JSON, SHA-256 of its own content, no secrets. It lists new migrations with their checksum, categories and review state, and states that backup and maintenance mode cannot be waived and that rollback is restore.
   Anything the manifest does not list is not claimed safe.
4. **Migration checksum and categories.** A migration's checksum is the SHA-256 of the SQL the migration engine generates from its `Up` operations (the history row is excluded). `MigrationInventory` classifies each migration (Destructive, DataRewrite, SchemaAlteration, IndexOrConstraint, RowLevelSecurity, RawSql). Migrations in the first three categories (they drop, rewrite or alter existing structure or data) need a **review entry** in `upgrades/migration-reviews.json`; the manifest builder and a test refuse a release without one. Baseline migrations that predate the ledger are recorded as `baseline-accepted`, which says so.
5. **Pre-flight (`IUpgradePreflight`, codes `UPF-nnn`).** A read-only report with four outcomes: **Ready**, **Ready with warnings**, **Blocked** and **Not Verified**. Every finding has a stable code, severity, plain explanation, technical detail, remediation and a correlation id. It checks the manifest (`UPM-nnn`), the database server and account, the installation's state against the baselines (**Empty, AtSource, AtTarget, Partial, Ahead, Inconsistent**), recorded migration checksums, **schema drift** against the model of the last applied migration, free storage, the named backup (existence, integrity re-checked now, age, environment, same installation, schema version it holds, data-loss window), maintenance mode and operations in progress, installation health (the validation engine's checks under an upgrade profile), and compatibility probes contributed by modules. It **fails closed**: any critical finding blocks; a warning needs the owner's explicit acceptance by code; a check that could not be made is Not Verified, never passed.
6. **Compatibility probes.** `IUpgradeProbe` (in `Ecp.SharedKernel`) lets a module report on its own content without the upgrade code knowing it: Configuration (`UPG-CFG-nnn`: published releases and open drafts against the validators of this version, kinds this version does not know; `UPG-PCK-nnn`: installed and shipped packs against the platform range, format and signatures), Lifecycle (`UPG-LIF-nnn`: signature requests, approvals and work in flight; contracts stay pinned to the workflow release they started under), Contracts (`UPG-VW-nnn`: saved views the new version cannot read), Notifications (`UPG-NTF-nnn`: outbox and running jobs) and Data Migration (`UPG-MIG-nnn`: a committing batch blocks). A probe reads; it never repairs, republishes, rewrites a release or moves a pin. A pack or release in use that would fail is a blocker; one nobody uses is a warning.
7. **Execution (`IUpgradeService`).** Apply is refused unless: the caller holds `operations.upgrade` in the installation tenant with a recent sign-in; the typed words name both versions (`UPGRADE <from> TO <to>`); the pre-flight for the apply phase passes (accepted warnings recorded); the manifest hash is the one expected, when the operator pinned it. It then takes two leases (`upgrade.exclusive` and `recovery.exclusive`, so no backup, restore or validation starts beside it), waits for background-job leases to drain (**quiescence**), applies migrations module by module in the deterministic tier order, records each applied migration and checksum in `ops.MigrationRecord`, runs post-upgrade validation and writes sanitised evidence. Maintenance mode carries cause `UpgradeInProgress`. On failure it becomes `UpgradeFailed` and **stays on**; leaving an upgrade-related maintenance state needs an explicit acknowledgement of the restore state. Nothing is retried, repaired or rolled back automatically.
8. **Maintenance gate.** `IMaintenanceGate` refuses configuration publication and rollback, and migration commit, from *any* caller (a service, a job, an API, a page), not only HTTP requests, so maintenance mode cannot be bypassed from inside the process.
9. **Rehearsal (`IUpgradeRehearsal`).** The same procedure against a **restored copy** in a new database (never the active one): restore the backup, run the pre-flight against the copy, upgrade the copy, validate it (data identical to the backup, policies, packs, configuration, audit chains, documents), run representative journeys and write evidence. The CI job does this on a real SQL Server with Blank, JBS Procurement and Harborline Construction populated.
10. **N-1 fixture, stated honestly.** "N-1" is the platform version before this release. The fixture is the **frozen N-1 schema** (the committed baseline ledger, applied by running the first N-1 migrations of each module), **populated by the current services** through their public interfaces, not a historical binary and not production data. It proves that this build upgrades that schema with real data in it and that the upgraded installation behaves; it does not prove that the N-1 *application* wrote exactly that data. This limit is written in `docs/UPGRADES.md` and in every report.
11. **Post-upgrade validation.** The validation engine gains a profile (`PostUpgrade`) and checks `UPV-001` (every migration recorded with the manifest's checksum), `UPV-002` (schema matches the final model), `UPV-003` (every module at the target schema version), plus the existing integrity, policy, audit-chain, document and pack checks.
12. **Operator interface.** Six pages under Administration, Operations (Upgrade Readiness, Upgrade Preview, Migration Report, Upgrade History, Post-Upgrade Validation, Rollback Evidence) and the commands `upgrade-preflight`, `upgrade-plan`, `upgrade-apply`, `upgrade-rehearse`, `upgrade-rollback-evidence`, `upgrade-history`, `upgrade-script`, `migration-report`, `upgrade-manifest-verify`, `upgrade-manifest-build`. A new permission `operations.upgrade` (System Administrator only) guards apply; rehearsal and rollback evidence use `operations.restore`; reading uses `operations.read`. Every call re-checks permission and installation tenant. Downloads (JSON, formula-safe CSV, pending-migration SQL for review) pass the secret scan.
13. **`migrate` in Production.** On a database that already holds an installation, the bare `migrate` command refuses and points to the upgrade procedure. It remains the way to create a first installation.
14. **Placement.** `MigrationInventory` is in `Ecp.Persistence` (it needs only module descriptors). `MigrationRecord` is in `Ecp.Operations` (additive migration `AddMigrationRecords`, table `ops.MigrationRecord` with row-level security). The upgrade code lives in `Ecp.Recovery` (tier 9) beside the restore code it reuses. Version is `1.1.0` (`Directory.Build.props`).

## Alternatives considered

* **Down migrations.** Rejected (D11.6 to D11.8): untested down scripts are the least trustworthy code in a system, and data written by the new version often cannot be expressed in the old schema. Restore is slower but is the path that is rehearsed.
* **Running the upgrade from a bare `migrate` with a warning.** Rejected: the failure mode is an operator who did not read the warning.
* **A historical N-1 binary in CI.** Not done in this slice: it would need the previous release built and run alongside; the frozen-schema fixture covers the schema risk, and the limit is stated. A release pipeline that keeps the previous container image can add it (listed in `docs/UPGRADES.md`).
* **Trusting the history table alone.** Rejected: the `__EFMigrationsHistory` row proves a migration was recorded, not that the schema is what it describes. Drift detection and recorded checksums close that gap on SQL Server.

## Consequences

* An operator can decide whether an upgrade is safe, rehearse it on a restored copy, apply it with evidence, and prove the way back, using commands and pages, without changing source code.
* Every release that adds migrations must ship a new baseline for the previous version, release notes, a rebuilt manifest and, for any destructive or rewriting migration, a review. Tests and the manifest builder refuse otherwise. `docs/UPGRADES.md` gives the release-engineering steps.
* Schema drift detection and checksum comparison run on SQL Server only; on SQLite the outcome is Blocked or Not Verified by design.
* The platform records what the operator states (reason, accepted warnings, sign-off) and never declares production readiness. Backup frequency, RPO, RTO, retention, change windows and approvals are the organisation's.
* Zero-downtime and multi-version operation are out of scope. An upgrade needs a maintenance window.
