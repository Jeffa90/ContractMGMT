# ADR-0027: The signature boundary is provider-neutral

Status: Accepted by the owner (portability slice S3, R6, 2026-10-17). Production approval remains external governance.
Amends ADR-0020 (the execution boundary keeps its three separate steps; only its vocabulary and shape change).

## Context

The execution boundary was shaped like one vendor: `IESignatureProvider.CreateEnvelopeAsync`, `EnvelopeRequest`, `EnvelopeResult`, a persisted `EnvelopeId` column and its filtered index, and an "Envelope" label on two pages (finding P-10, `docs/PORTABILITY_AUDIT.md`). No adapter existed yet, so the rename was cheap; after a first adapter writes data it would not be. DocuSign is one optional future provider. Its terms must not define platform entities, columns, interfaces, routes, configuration keys or labels.

## Decisions

| # | Decision |
|---|---|
| D1 | The platform's vocabulary is: **Signature Request**, **Signature Provider**, **Provider Request ID**, **Signature Request Status** (Sent for Signature, Delivered, Completed, Declined, Voided, Expired, Failed), **Executed Document**, **Provider Event**, **Provider Callback**, **External Execution**. Envelope, Envelope ID, DocuSign Envelope, DocuSign Status, Recipient Tabs and DocuSign Connect are not platform concepts. Vendor-native words may appear only in a provider adapter, its configuration page and its integration notes (`requirements/07-integrations/DOCUSIGN_ADAPTER_NOTES.md`). An architecture test fails the build if they appear anywhere under `src/` (except the one compatibility name in D9, and historical migrations). |
| D2 | Legal clearance, External Execution and register authorisation stay three separate events. A signature request can only supply the executed copy that the `ExecutedCopyExists` guard looks for. It never approves, registers, locks or makes a contract Effective. |
| D3 | `ExecutionRecord` becomes `SignatureRequest`: tenant, organisation, subject and contract ids, provider key, **Provider Request ID (optional until a provider accepts the request)**, platform status, the provider's native status kept **separately** (`ProviderStatus`), requested by and when, last provider event time, completed time, executed-document reference, correlation id, **idempotency key**, failure code and sanitised failure message. Status values are platform words only; `Sent` is displayed as "Sent for signature". |
| D4 | Interfaces (all in `Ecp.Lifecycle`, none carries a vendor type): `ISignatureProvider`, `ISignatureRequestService`, `ISignatureStatusMapper`, `ISignatureCallbackVerifier`, `ISignatureEventInbox`, `IExecutedDocumentRetriever`, plus `ISignatureProviderFactory`. A provider's payloads stay inside its adapter. A new adapter registers its classes; the lifecycle engine does not change (proved by a test adapter with its own words, headers, secret and payload). |
| D5 | **Provider-native statuses never control the contract.** They are mapped by the provider's `ISignatureStatusMapper`. A word the mapper does not know changes nothing: it is kept on the request and in the inbox (outcome *Unmapped*) where an administrator can see it. |
| D6 | **Every provider event is idempotent.** The inbox keeps one row per (tenant, provider, provider event id), unique. A repeat is acknowledged and changes nothing; an event whose processing failed or was interrupted is tried again on redelivery. Outcomes: Applied, Ignored (superseded request, request already ended, or older than what is recorded), Unmapped, Unknown request, Failed. Provider payloads are not stored. |
| D7 | On Completed the executed document is retrieved and stored through the normal document service (type, size, scan, hash, classification, storage). If it is refused or unavailable the request records a failure code and message, keeps its status, and the event is *Failed* and visible; redelivery retries. Every status change and every unhandled event is audited. Tenant and organisation isolation and document permissions apply unchanged; an event for another tenant's request matches nothing. |
| D8 | The mock provider, its callback verifier and simulated events are refused in Production (as before). Manual executed-copy upload remains supported and is a provider (`manual`). The placeholder for a live provider (`external`) still fails closed. **No live DocuSign adapter and no callback HTTP endpoint are built in S3.** `HmacCallbackVerifier` (HMAC-SHA256 over timestamp and raw body, constant-time compare, 5-minute freshness) is provided for adapters. |
| D9 | **Compatibility.** (a) The table and four columns are renamed in place and no value is rewritten (EF migration `SignatureRequestVocabulary`): `ExecutionRecord`→`SignatureRequest`, `EnvelopeId`→`ProviderRequestId`, `StartedBy`→`RequestedBy`, `StartedUtc`→`RequestedUtc`, `ExecutedUtc`→`CompletedUtc`; indexes and the primary key are renamed; the filtered index is re-created; new columns start empty; the row-level-security policy is re-created under the new table name. (b) Contract state, approval records, executed-document references and audit records are not touched; audit action codes (`execution.*`) are kept, and historical audit text is not rewritten. (c) Register-authorisation snapshots frozen before the rename carry `envelopeId`; they are evidence and are never rewritten, so `RegisterSnapshot` reads that key (`LegacyRequestId`) and folds it into `ProviderRequestId`; new snapshots write only `providerRequestId`. (d) Workflow definitions and packs use `sendSignature`, the `signature` state role and the guard name `SignatureVoidedOrDeclined`; these are already neutral and are unchanged. The guard is *extended* (it now also holds when a request is Expired or Failed, which did not exist before) and keeps its name so published definitions stay valid. |
| D10 | Not in S3: a live DocuSign adapter, the callback endpoint (`POST /api/v1/integrations/signature/{providerKey}/callback`, Future), a provider-configuration page, reporting, operations, role-catalogue replacement, feature flags, another pack slice. |

## Consequences

* P-10 is closed. The next provider is an adapter, not a schema change.
* The migration is forward-only in production use; rollback is by restoring the pre-upgrade backup (a `Down` exists for development and drops the new inbox table's data).
* The migration is applied only on SQL Server; the lightweight provider builds its schema from the model. Its data-preserving behaviour is therefore proved by a SQL Server test (`SignatureVocabularyMigrationTests`) that runs in CI, and is reported NOT VERIFIED without one.
