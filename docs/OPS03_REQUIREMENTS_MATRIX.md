# OPS-03 requirements matrix (written before implementation, 2026-10-18)

Source of truth for scope: `TASKS.md` row **OPS-03** ("Maintenance mode; operations dashboard (health, readiness, jobs, outbox, certificates)", depends on SET-03, acceptance **BRS-004**), `requirements/12-operations/OPERATIONS_SPEC.md` (one paragraph) and `requirements/12-operations/SETUP_AND_READINESS_SPEC.md` section 6 ("Operations dashboard"), with the readiness catalogue in its section 4. `docs/PROJECT_STATUS.md`, `docs/OPERATIONS_RUNBOOK.md` and `docs/PRODUCTION_READINESS_CHECKLIST.md` restate the remainder as "certificate, outbox and job panels".

## 1. Contradictions and dependency gaps recorded before implementation

| ID | Finding | Resolution (reversible assumption) |
|---|---|---|
| C-1 | OPS-03 depends on **SET-03**, which is unticked: "the full R-* catalogue is not built". Spec section 6 says the dashboard shows "the same checks" as the readiness catalogue. | OPS-03 does not build the missing checks (that is SET-03). The dashboard runs every check that exists, and lists every catalogue entry that has **no check** as **Not Verified: check not built**, never as passed. SET-03 stays open. |
| C-2 | Spec section 6 gives the dashboard to holders of `ops.manage`. That permission does not exist; owner decision D10 / ADR-0034 created `operations.read`, `.backup`, `.restore`, `.validate`, `.maintenance`, `.evidence.export`, `.upgrade`. | `ops.manage` is read as the D10 permission set. The dashboard needs `operations.read` (System Administrator only); technical detail needs `operations.validate`. No new permission. |
| C-3 | The support bundle (redaction, SEC-030, SEC-031) and monitoring/SIEM sinks (INT-04) are assigned to **OPS-04** and **INT-04** in `TASKS.md`, yet the brief lists "support-bundle generation" and observability under the OPS-03 operations experience. | Implemented here only what the **dashboard needs and the brief names as gaps**: bundle generation from the dashboard with recent sign-in and audit, a deterministic manifest with file hashes, size and entry limits, a formula-safe summary, and job/outbox/lease/certificate facts in the bundle. The SEC-030/SEC-031 catalogue and OPS-04 stay open and unticked. Observability is the standard .NET `Meter` plus structured log events and a local snapshot; OpenTelemetry, SIEM and syslog **sinks are not built** (INT-04) and are labelled Not Verified / Future. |
| C-4 | Spec section 6 lists "certificate and secret expiry warnings". The platform holds no certificates it can inspect except: pack-signing public keys (validity dates), the data-protection key ring (key expiry), and the optional SQL Server backup-encryption certificate. TLS is normally terminated outside the application, and secrets are resolved by reference with no expiry metadata. | Panel shows those three sources where readable, and shows **TLS certificate** and **secret expiry** as **Not Verified** with the reason. No external certificate store is queried. |
| C-5 | "Last restore-test evidence" and "migration batches in progress" (spec section 6) span OPS-01 and Data Migration. | Reused from `IOperationHistory` (restore and validation runs) and the Data Migration upgrade probe's committing-batch count, via a neutral operational probe. |
| C-6 | Installation-level operators sit in the installation tenant; background jobs and the outbox are tenant data under row-level security. A dashboard must not read another tenant's records. | The dashboard reads **counts and timestamps only**, per tenant, inside that tenant's scope, through module-provided probes. Retrying a customer tenant's dead-lettered message remains a tenant-administrator action in that tenant's own Notifications page. The operator dashboard offers no cross-tenant retry. |
