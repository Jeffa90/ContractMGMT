# Setup and Readiness Specification

Added by repository review (GAP-19, CON-06, RISK-05, RISK-17). Master lists 18 installation-wizard stages as titles and says "Production mode refuses development identity, default credentials, ephemeral storage, exposed secrets and unresolved critical readiness failures." This file gives each stage acceptance criteria and enumerates the readiness checks. Tags: `[CONFIRMED]` traceable to Master or `OPERATIONS_SPEC.md`; `[CONFIRMED]` detail.

## 1. Setup security model `[CONFIRMED]`

1. **Bootstrap store.** Before the database exists, setup state and secret *references* live in a protected bootstrap store (a file in the data directory, values protected by the Data Protection API or the host secret provider). Once the database is migrated, setup state is mirrored to the database and the bootstrap store keeps only what is needed to reach the database (ASM-10, CON-06).
2. **Setup token.** On first start the platform generates a one-time random setup token (at least 256 bits), prints it once to the console/log of the host, and stores only its hash. `/setup` requires it. It expires (default 24 hours; regenerated by a host-level command, never over HTTP). Without a valid token `/setup` returns 404. This prevents takeover of an internet-exposed fresh install (RISK-05).
3. **Network posture.** Default is to accept setup requests only from loopback or from a configured allowlist; widening it is a host-level setting, not a wizard option.
4. **Single session.** One setup session holds a lock; a second concurrent session is refused.
5. **After completion.** `/setup` routes are removed from routing (not merely hidden). Later changes happen in the administration console and require `setup.run` or the relevant admin permission **with step-up re-authentication** `[CONFIRMED]`.
6. **Secrets.** In Production the wizard never accepts, stores or displays a secret value: it validates that the configured secret references resolve (environment variable, Docker secret, Key Vault, DPAPI-protected file). In Demo and Test it may write generated, non-sensitive values to the protected local store (ASM-11).
7. **Resumable and idempotent** `[CONFIRMED]`: each stage has a status (`NotStarted`, `InProgress`, `Complete`, `Skipped`) and can be revisited; re-running a stage with the same input changes nothing; the wizard survives restarts and browser closure.
8. Normal pages are unavailable until setup completes `[CONFIRMED]`.

## 2. Stage order

Master numbers stay as identifiers (S1 to S18). Dependencies mean the **execution order** must differ from numeric order (CON-06; proposed amendment PA-2):

`S1 → S2 → S3 → S4 → S6 → S7 → S8 → S9 → S10 → S11 → S12 → S5 → S13 → S14 → S15 → S16 → S17 → S18`

Reason: the database and identity (S6 to S9) must exist before organisation data can be stored (S5, S13 to S15), and the solution pack (S12) supplies terminology, branding, workflow and rule defaults that S5 and S14 then tailor.

## 5. Sanitised setup report

A downloadable report (HTML and JSON): mode, deployment model, versions, stage statuses with times, readiness results with severity, integration statuses (Disabled/Mock/Configured), selected pack and release id, administrators (names only), unresolved warnings with the acknowledging user and reason. **Excluded:** secrets and secret references' values, connection strings, tokens, hostnames of internal systems beyond what the operator opts in, and any business data. Production readiness is "evidence for the owner", never an approval: the report states that formal production approval is external governance (`CLAUDE.md`).

## 6. Operations dashboard

The same checks, plus job and outbox health, last backup and restore-test evidence, migration batches in progress, configuration release in force, and certificate and secret expiry warnings, are shown to holders of `ops.manage`. Detailed dependency information is never shown on unauthenticated health endpoints.
