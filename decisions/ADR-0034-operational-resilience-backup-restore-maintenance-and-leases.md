# ADR-0034: Operational resilience: backup, restore, validation, maintenance mode and operation leases

Status: Implemented by slice OPS-01 / OPS-02 foundation (2026-10-17). Proposed until the owner reviews it; production approval remains external governance.
Builds on ADR-0003 (tenant isolation and row-level security), ADR-0011 (audit chain), ADR-0012 (document storage), ADR-0026 (external packs), ADR-0028 to ADR-0033 (portability slices S4 to S10). Owner decisions: `requirements/01-authoritative/CONFIRMED_DECISIONS.md`, section D10.

## Context

The portability programme (S1 to S10) is complete: Blank, JBS Procurement and Harborline Construction run on one platform, each configured by data. What was missing is the ability of a trained operator to **create, verify and restore a complete installation backup without changing source code or relying on undocumented knowledge**. Data lives in four places that must come back together: the SQL Server database (every module schema, the migration history, the audit chain, published configuration, installed pack records and the trust store's public keys), the document store, the installed package bytes, and secrets (which must not travel). A backup that restores only one of them, or that cannot say whether it is intact, is worse than none.

## Decision

1. **SQL Server is authoritative.** Database backup uses `BACKUP DATABASE ... WITH CHECKSUM` (COPY_ONLY by default, so the operator's own backup chain is untouched), verification uses `RESTORE VERIFYONLY ... WITH CHECKSUM`, and restore uses `RESTORE DATABASE`. There is no logical export that pretends to be a backup. SQLite is for demonstration and tests only and refuses backup. Azure SQL is not implemented (its backups are managed by the service) and is documented Not Verified.
2. **A backup is a directory with an immutable id** (`bk-yyyymmddThhmmssZ-xxxxxxxx`), outside any served path: a database folder (the `.bak`), a documents folder (every object at its content address plus an index with a SHA-256 per object), a packs folder (installed `.ecpkg` bytes), an inventory file, and a deterministic `manifest.json` written last with its SHA-256 in `manifest.sha256`. A folder without a manifest is Incomplete or Failed and is never a recovery point. A backup is never overwritten, and it is **not reported successful until it has been read back and verified**.
3. **The manifest holds identifiers, counts and hashes, nothing else**: format version, platform version, environment mode, database engine, version and backup type, per-module applied migrations, enabled row-level security policies, document and package inventories, per-tenant audit-chain head, configuration release fingerprints, per-organisation regional fingerprint, per-table row counts and content checksums before and after the database backup, protection status, warnings, operator and correlation id. Every manifest is scanned for secrets before it is written.
4. **Restore is installation-level and goes beside the running installation.** It restores into a **new** database, a new document directory and a new package directory, opens that copy with the same module composition (`PlatformComposition`), holds it in maintenance mode, runs post-restore validation, and releases it only if validation passes. The active database is never the target (identity is compared as the server reports it, so an alias cannot disguise it). Restoring over the active database exists only as an explicit disaster-recovery path from the command line, with its own confirmation phrase. Restore applies no migrations, regenerates no history, republishes no configuration and rewrites no identifier or hash.
5. **Documents go through the storage abstraction.** `IDocumentStoreInventory` lists a provider's objects; the local file system provider implements it (links and unexpected names are skipped, never followed). A provider that cannot list its objects is reported as "document content not backed up by the platform". No SharePoint or Azure Blob provider exists and none is claimed.
6. **Secrets never travel.** Backups contain secret references (names), never secret values or private signing keys; only public trust keys are recorded. Free text that reaches a manifest, an audit event or a report (a reason) is masked first, and every finished document is scanned again and refused if a secret remains. The privileged backup account is a separate secret.
7. **Post-restore validation is a product feature** (`IInstallationValidator`, codes `VAL-nnn`): connectivity, migration history (and "never apply migrations automatically"), tables, counts and checksums against the backup, referential integrity, row-level security policies and session-context behaviour, audit chains and their anchors, document metadata against content (re-hashed), installed packages and signatures, configuration release hashes, pinned workflows, contract-document links, outbox consistency, regional resolution, tax-identifier projection and organisation readiness; plus DBCC CHECKDB. Outcomes: Passed, Passed with warnings, Failed, Not Verified. Only the first two release a restored copy.
8. **Maintenance mode** is one installation flag with a reason and a cause. While on: requests that change state are refused with 503 and `Retry-After` (reads, health, sign-in and the Operations pages stay open), background jobs take no new work, every page shows a banner. A restore that is in progress, waiting for validation or failed cannot be left by accident: leaving needs an explicit acknowledgement. Every transition is audited.
9. **Operation leases** are SQL-backed singleton claims (unique key plus optimistic concurrency): backup, restore and installation validation share one lease (`recovery.exclusive`), and each tenant's background-job cycle holds its own. Owner, acquisition, heartbeat and expiry are recorded; an expired lease is taken over safely and audited; an operator can take a lease over with a reason (audited), and the old owner's next renewal fails so it stops.
10. **The operator interface is `Administration, Operations`**, guarded by six new permissions held only by the System Administrator (`operations.read`, `.backup`, `.restore`, `.validate`, `.maintenance`, `.evidence.export`). Each service call re-checks the permission and that the caller is in the installation's own tenant; state-changing actions need a recent sign-in; restore needs a reason and a typed phrase naming the backup. The web interface cannot restore over the active database.
11. **Evidence and support are sanitised by construction.** The evidence report (JSON and formula-safe CSV) and the support bundle (versions, statuses, counts, redacted recent log lines, deployment-model status) exclude secrets, connection strings, keys, record and document content and personal data, and say plainly which deployment models are Verified and which are not.
12. **Placement.** `Ecp.Operations` (tier 8) gains an `ops` schema (`OperationLease`, `MaintenanceState`, `OperationRun`; additive migration `Initial`). The orchestration lives in a new project `Ecp.Recovery` (tier 9) because it needs Audit, Tenancy, Identity, Configuration and Documents. It reads other modules through trusted, read-only interfaces added for it (`IConfigurationInventory`, `IDocumentIntegrity`, `IDocumentStoreInventory`) and through fixed, reviewed, parameter-free SQL for table counts and database-level checks, derived from the EF models. The Host composes everything (`PlatformComposition`), so a restored copy is opened with exactly the same services.

## Consequences

* An operator can run a rehearsal that proves, with evidence, that a populated installation (the three shipped businesses) comes back with the same audit heads, releases, packs, documents, wording, capabilities and regional settings. CI does this against a real SQL Server on every push.
* The platform now needs an operator-provided **shared backup directory** between the database server and the application (the server writes the `.bak`; the application hashes it and records it). This is documented as an operator responsibility with the Linux permission pattern CI uses.
* Restoring does not make anything switch over: pointing the application at a validated copy is a deliberate configuration change (`docs/OPERATIONS_RUNBOOK.md`).
* Backup frequency, retention, RPO and RTO, storage encryption and access control, restore rehearsal schedule, point-in-time recovery and sign-off are the **organisation's** to define; the platform provides tooling and evidence, records what the operator states, and never declares production readiness.
* Limitations are documented, not hidden: one lease name serialises backup, restore and validation; checksums read every table; document inventories are held in memory; the maintenance flag is refreshed by other instances within three seconds; per-tenant backup and restore, differential or log backups, point-in-time recovery, Azure SQL, SharePoint and Blob providers are Future.
* Alternatives rejected: a logical per-table export as the backup (cannot prove a faithful copy, cannot carry row-level security or constraints, invites silent partial restores); restoring over the active database from the web interface (too easy to do by mistake); trusting the manifest alone (it is self-consistent when forged, so the hash is also recorded in the audit trail and run history, and a restore can be told the hash to expect); in-process locks for singleton work (do not hold across instances).
