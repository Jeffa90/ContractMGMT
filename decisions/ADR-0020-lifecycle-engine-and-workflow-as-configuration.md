# ADR-0020: Lifecycle engine, workflow definitions as configuration, and the execution boundary

Status: Accepted (lifecycle slice, DR-2026-10-16)

## Context

`CLAUDE.md` requires the JBS lifecycle to be a shipped reference configuration, not hard-coded logic, with draft/validate/preview/publish/rollback/audit, no customer code, server-side enforcement and immutable Effective contracts. The slice must also deliver structured Legal review, an e-signature boundary, register authorisation, force-unlock, Variations and renewals without a visual designer.

## Decision

1. **A new `Ecp.Lifecycle` module (tier 7)** owns workflow definitions, the transition engine, status history, Legal review, execution records, register authorisation, unlocks, Variations, renewals and the lifecycle outbox. It reaches contract state only through `IContractLifecyclePort` (Contracts module), never its tables.
2. **Definitions are Configuration kinds** (`WorkflowContractLifecycle`, `WorkflowVariation`) with the existing draft, validate, publish, rollback and history. The pack JSON is installed on first use. A definition is *data in a closed vocabulary*: states with roles and effects (lock, freeze content, document policy), transitions with a permission from the catalogue, a transition role and a list of named guards. Unknown JSON members, unknown guards, roles, permissions or fields are errors; there is no expression language, script, SQL or template logic. Validation also rejects dead ends, transitions that unlock a locked record, an approval that does not land in a locked state, approving without the `AuthorisedApprover`, `SubmitterNotApprover` and `ExecutedCopyExists` guards, unbounded unlock settings and second-person unlock (not supported yet).
3. **Pinning.** A contract pins `WorkflowRef` and `ConfigReleaseId` at creation. Publishing a new release affects new contracts only; existing contracts continue on the release they were created under until a deliberate migration (Future).
4. **The engine is the only writer of status.** Order of checks: contract visible (404) → permission (403) → idempotency by `ClientRequestId` → from-state → expected state (stale screens) → managed-role check → guards. One unit of work then writes the contract state through the port, a `StatusHistory` row with a per-contract sequence, a `LifecycleEvent` outbox row and the audit event. A crafted API call cannot bypass any check, and the generic transition call refuses *managed* roles (Legal, signature, approval, Variation, renewal) that must go through their services.
5. **Legal review is structured data.** One review per subject; rounds are never overwritten; comments are threaded; attachments are documents of the contract; assignment is to a named reviewer from the Legal pool; owner response and resubmission start a new round. The queue has filters and an outstanding-for-me view.
6. **Execution boundary.** Clearance by Legal, execution (signature) and register authorisation are three separate steps. `ISignatureProvider` (named `IESignatureProvider` when this ADR was written; renamed by ADR-0027) has a Manual provider (the owner uploads the executed copy; Implemented), a Mock provider (Demo/Test only; refused in Production) and an external-envelope adapter scaffold that stores envelope id and status but has no live credentials (Scaffolded, Not Verified). An executed copy is required before register authorisation.
7. **Register authorisation.** The Group Head of Procurement (approver group key from the definition) or a backup may respond. The request holds an immutable snapshot with a SHA-256 checksum of what was executed and registered. The first response wins; a concurrent second response gets `already_decided`. The submitter cannot approve. Approval stamps the Registered Date in UTC and moves the contract to a locked Effective state; rejection returns it to Initial Creation with the reason. Approvers can read a contract only while a request is pending (or for a disposition they are asked to decide), via `IPendingApprovalSource`.
8. **Effective contracts are immutable.** Changes happen only through an approved Variation (field list from the Variation definition, before and after stored, parent stays locked) or an audited **emergency unlock**: permission `contracts.unlock_emergency`, recent re-authentication, reason of at least 20 characters, a time limit within the definition's maximum, classification never offered, only the opener may change fields, automatic re-lock at expiry by a background job. Second-person confirmation is Future and refused by validation rather than silently ignored.
9. **Variations and renewals** run their own workflow. One open Variation per contract (filtered unique index). A renewal creates a draft successor from configured fields and document types only, links both ways, never alters the predecessor, and cancelling withdraws the draft and restores the predecessor.
10. **Outbox.** Every event is written in the same transaction as the change; the Notifications dispatcher consumes it (ADR-0021).

## Consequences

* Business administrators can change guards, states, transitions, permissions per transition, unlock limits, renewal copy rules and Variation fields by publishing a release; nothing in the engine knows the JBS state names except through roles.
* The vocabulary is intentionally small. New guard kinds, state roles and managed roles are code changes with tests; this is the boundary that keeps customer configuration from becoming code.
* A visual workflow designer and an approval-matrix designer are not built; the JSON is edited through the configuration administration pages with validation messages.
* Residual: pinned contracts cannot yet be migrated to a new release; retention periods and legal holds are scaffolded behind `IDispositionChecks` (default: no blocks) and are **not** a retention policy.
